# World replies, persona text, and approved activity continuity

Status: implementation and validation in progress. This change must stop before
merging `main`; CI, contributor checks, installed-app USER CHECK, merge, and
release are separate gates.

## Product behavior

Editing a character persona does not invalidate a previously approved World
profile/repertoire merely because the current character hash changed. The
approved pair keeps its generation hashes. A user may explicitly generate a new
candidate, review it, approve it, or reject that exact candidate. Generation,
failure, and rejection preserve the active approved pair. Approval supersedes
the pair atomically. Existing daily plans retain their repertoire and candidate
references; subsequently created plans use the newly approved pair.

World publication/readiness, active membership, role eligibility, actor scope,
candidate validity, and World definition compatibility still apply. Persona
continuity is not permission to execute an invalid World or role. The autonomy
switch and the selected active World are preserved during regeneration.

## Persona storage and package compatibility

Lengths are Unicode code points after CRLF/CR to LF and NFC normalization, before
existing surrounding-whitespace trimming. JavaScript uses `Array.from` rather
than UTF-16 `maxlength`. Inputs keep over-limit drafts, show a counter and a
field-associated error, and block submission until corrected. Direct writes,
creation drafts, AI enhancement admission, and seed import also validate.

| Field | Maximum code points |
| --- | ---: |
| one_liner | 500 |
| personality | 6,000 |
| speech_style | 4,000 |
| worldview | 8,000 |
| topic_preferences | 3,000 |
| safety_rules | 4,000 |
| persona_summary | 32,000 |

The six editable fields total 25,500; the existing labels and separators add at
most 35, leaving 6,465 characters of summary headroom. Stored summaries are not
silently truncated or regenerated by AI to permit export. The previously failing
2,019-character summary fits without editing.

Exports now use format version 2 / `world-package-v2`, with
`characters-content-v2` and minimum reader version `0.4.0-2`. V2 topic and safety
fields are strings, preserving commas, whitespace and line breaks instead of
splitting them into lists. V1 schemas and their golden hashes remain frozen;
the reader still accepts valid v1 archives. Old readers reject format 2. Other
content documents keep their v1 contracts. This is a Local reader/writer change;
it does not certify Nest's acceptance of the new format.

Only v2 `content/characters.json` has a 32 MiB JSON budget. Other JSON entries
remain at 2 MiB, manifest/license text at 256 KiB, images at 5 MiB, 50 characters,
100 assets, 128 MiB compressed archive and 256 MiB expanded archive. Path,
duplicate, compression-ratio, digest, media and atomic-import checks remain.
Metadata admission uses a bounded potential-v2 allowance; the validated
manifest then applies the exact version's entry budget before content parsing.

Storage limits do not promise that all persona text enters every LLM prompt.
Existing prompt consumers have separate budgets: routine-post evidence and feed
reaction clip summaries to 1,500 characters, writing context to 900, resident
selection to 240/300/1,200; other legacy prompt builders interpolate the stored
summary. These admission changes do not increase provider output caps or invoke
AI automatically. Prompt-wide budgeting remains a separate concern from package
serialization, and token use may increase for consumers that use the full text.

Export conversion errors become a handled 422. Persona errors expose only the
field name and numeric limit/length, not field content or internal validation
input. Admitted desktop requests retain exact-origin CORS on an unhandled 500,
so an HTTP failure is not misreported as a disconnected runtime. Authentication,
token and origin admission run before that error path.

## Thread read contract

`GET /worlds/{world}/manual-social/posts/{post}` accepts a root or any visible
descendant. The response adds `root_post_id`, `target_post_id`, `page_offset` and
`next_offset`. The first item is the root; the remaining items are a page of
visible descendants ordered by creation time and ID. `reply_to_post_id` retains
the direct parent. `reply_count` now counts all visible descendants, consistently
on feed cards and the detail heading; it is not the current page length.

The default page size is 50. Without an explicit offset, a reply URL opens the
page containing that reply. An explicit offset allows previous/next-page
navigation. Existing reply URLs used by Chat and Memory therefore continue to
identify the exact source; no evidence source ID or revision is rewritten to a
root ID. The common Next/static component scrolls to and marks the target and
links to its parent, even if the parent is on another page.

Traversal follows only public, non-deleted, non-report-hidden ancestors in the
same World. Inaccessible branches, cross-World parents and disconnected cycles
do not resolve. Recursive UNION terminates cycles. Page rows are bounded;
counts, authors and block relationships use grouped/batched queries rather than
one lookup for each reply. Owner/membership admission precedes traversal.

## Optional generation and concurrency

The generation request adds `regenerate`, default false for existing callers.
An explicit true request creates a new profile/repertoire even when inputs are
unchanged. Replays retain idempotency and do not make another provider call.
The preflight query `regenerate=true` quotes two logical / three physical calls.
Existing setup quota and provider controls still apply.

Setup reads separate `active_profile` / `active_repertoire` from the reviewed
`profile` / `repertoire`, with `persona_changed` and `can_reject`. Rejection
requires exact candidate profile/repertoire IDs and never mass-updates ready
rows. Approval verifies the reviewed IDs and current input hashes. Running
attempt checks plus compare-and-swap on the existing WorldCharacter version
serialize setup mutations on SQLite. Claims commit before awaiting a provider;
late result admission rechecks the scope and hashes.

## Design provenance and validation gates

- DIRECT: shared Field/Textarea error, helper text, Card and Button primitives.
- ADAPTED: field counters and approved-result/candidate messaging for Local.
- LOCAL: exact-reply highlight, parent link and bounded thread page navigation.
- REJECTED: native maxlength truncation, mandatory persona regeneration, and
  rewriting evidence identity to a root post.

Focused tests cover Unicode boundaries, maximum 50-character package roundtrip,
safe errors, hidden ancestors/cycles/paging, preserved approval provenance,
failure/rejection, idempotency and old/new daily plans. Browser tests exercise
overflow correction, reply targeting, and optional generation. Full backend,
Next/static builds, public contract/architecture inventories, contributor Docker,
PR CI and installed USER CHECK must be recorded separately in the PR.

No merge, release, installed-data rewrite or successful USER CHECK is implied by
this document or by automated test success.

## Preservation after the structural refactor

PR316 intentionally changes product behavior after AR-X. The historical source,
API/ORM checkpoints and original frontend browser oracles remain immutable.
`security/post_refactor_contract_changes.json` records only the exact before/after
OpenAPI operation/schema hashes and four behavioral assertion sets required by
this change, with implementation commit/blob provenance and the PR for review.
The preservation checker applies those entries to a copy of the old expectations;
it still rejects unlisted API drift, ORM changes, missing tests, assertion deletion,
and edits to prior change records. New sources/tests retain the existing
append-only introduction ledger. This does not imply PR review or USER CHECK passed.

Each thread row carries `thread_root_post_id` verified by the server so a later
page can retain ancestry proof even when its parent is on a different page.
Legacy direct replies remain readable; unrelated same-World rows fail validation.


V1 compatibility retains its frozen schema and list representation. Because v1
list items had no individual length bound, the reader also checks their joined,
normalized persona text against current storage admission before producing a
preview. Oversized legacy lists receive safe field/limit/actual details instead
of failing later during seed writes. The same safe error translation is used by
export and import validation. Valid in-budget v1 content remains unchanged.

# PostgreSQL 실험의 기억·관계 정리 복구 계약

기준: 2026-10-29, `experiment/postgresql-termux`. 이 문서는 해당 격리 실험의 구현 계약이며, 기존 SQLite 제품의 배포 완료를 뜻하지 않는다.

## 실행과 실패

기존 단일 backend 안에서 캐릭터 한 명의 기억 저장 run 또는 관계 정리 request를 선택해 연속 처리한다. 자동·수동 요청은 같은 접수 순서와 실행 가능 여부를 따른다. 기억 저장과 관계 정리는 별도 차례이며, 정상 처리 중 기억 한 건·관계 상대 한 명을 마쳤다는 이유로 다른 캐릭터에게 넘기지 않는다.

`memory_maintenance_slot`에는 프로세스 identity, 선택한 World·캐릭터·종류·요청 ID와 실행 token을 짧은 트랜잭션으로 기록한다. 기억은 각 건을 짧게 준비·저장하고, 최대 32건마다 이벤트 루프에 양보하면서 같은 run을 계속 처리한다. 관계는 해당 요청의 상대별 root와 분할 자식만 이어서 처리한다. 처리 중 추가된 기억은 고정된 cutoff/snapshot 밖에 남는다. 임베딩 최대 20개 묶음과 마지막 소량 입력 처리는 유지한다.

정상 AI 대기 중 차례는 유지하되 DB 연결·행 잠금은 유지하지 않는다. 완료·취소·실패 확정 또는 장래 재시도 대기에서는 차례를 반환한다. 다른 실행자가 소유권을 가져오려면 이전 프로세스의 종료를 증명해야 한다. SNS·Chat·검색은 별도로 진행한다. 5초 대기는 유휴 구간에 적용하며, 같은 run의 준비된 기억 사이에 넣지 않는다.

자동·수동 관계 정리는 같은 durable request와 상대별 work/receipt를 사용한다. 실행·대기·실패·사용자 종료를 구분한다. 실패한 work는 자동 선택에서 제외하고 새 정상 입력과 다른 캐릭터의 요청을 계속 진행한다. 기억 저장도 실패 run의 미완료 receipt를 일반 예약이나 새 저장 요청에 다시 포함하지 않는다.

실패 후 `close_without_retry`를 선택하면 연결 receipt를 `excluded/owner_closed_failure`로 기록한다. 실패 work·응답·완료 결과·요청 snapshot은 보존한다. 새 요청의 pending receipt 편입에서는 실패·수동 복구 대기를 제외한다. 같은 상대의 새 기억은 정상 대상으로 허용한다. 새 대상이 없으면 새 검토나 AI 호출을 만들지 않는다.

PostgreSQL v5 업그레이드는 종료 시각이 후속 요청 접수보다 앞선 경우만 과거 실패 혼입으로 식별한다. 원래 snapshot/work ID 목록을 보존하고, `maintenance.prior_failure_memory_ids/work_ids`에 새 회차에서 제외할 근거를 기록한다. 조회는 이 목록을 적용해 대상·완료·유지·갱신·실패를 계산한다. 사용자가 해당 회차에서 직접 종료한 실패는 그 회차의 실제 이력에 남는다. 업그레이드는 반복 적용해도 같으며 AI를 호출하지 않는다.

관계 검토 입력은 상대별 상황기억 본문과 기존 관계 인식이다. 원문을 재조회하거나 스냅샷을 관계 AI에 전달하지 않는다. SNS·Chat의 원문 스냅샷 계약은 유지한다.

## 받은 결과와 재시도

- 저장 대상 문자열에서 NUL과 잘못된 surrogate를 거절한다. 정상 한영·이모지·줄바꿈과 리터럴 escape는 유지한다. 잘못된 결과를 임의로 고쳐 성공으로 표시하지 않는다.
- 사용할 수 없는 결과는 private rejected journal에 보존하고 재생 대상을 제거한다. 같은 응답의 자동 저장·재생성 반복은 없다. World 삭제는 정상·격리 journal 모두 닫는다.
- 관계 provider는 SDK 전송을 1회로 제한한다. 429·503은 durable work의 시도 수를 기준으로 최초 포함 최대 2회만 전송한다. 일반 요청·재시작은 이 예산을 초기화하지 않는다.
- DB 트랜잭션의 4회·5초 제한을 재사용한다. 받은 결과의 저장은 최대 3라운드·120초 안에서만 자동 재개한다. 라운드 사이에는 5초·15초와 작은 분산 지연을 둔다. 한도 소진 후 유효 응답은 보존하고 수동 저장 재개만 허용한다.
- SNS 공개 행동은 기존 execution signature와 checkpoint를 사용한다. 답글·게시 효과와 완료 receipt를 같은 트랜잭션으로 확정하고, DB 실패 때문에 AI를 다시 호출하지 않는다. 저장 결과가 불확실하면 성공 기록을 먼저 대조하고 무조건 재게시하지 않는다.

## 사용자 명령과 표시

진행 응답 `workflow_version=2`는 `revision`, `actions`, `requires_new_ai_call`을 제공한다. 클라이언트는 서버가 허용한 동작만 표시한다. 명령에는 `idempotency_key`, `expected_revision`, `mode`가 필요하다. 요청의 owner/World/캐릭터 범위를 검증하고 revision 경합을 거절한다. 이미 처리된 같은 키는 같은 효과를 반환한다.

| mode | 의미 |
| --- | --- |
| `cancel_remaining` | 남은 실행 중단. 완료 결과 유지, 늦은 결과는 실행권 검사로 차단 |
| `resume_remaining` | 취소된 요청의 남은 범위만 명시적으로 재개 |
| `resume_storage` | 이미 받은 유효 응답의 DB 저장만 재개 |
| `regenerate_failed` | 실패 부분을 다시 판단. 새 AI 비용 안내 |
| `close_without_retry` | 실패 복구 종료. 성공·실패 이력을 보존하고 자동 재실행에서 제외 |

분할 검토에서 받은 부분 결과는 취소·재개에도 유지한다. 저장 실패와 사용할 수 없는 응답이 섞이면 각 실패에 맞는 저장 재개·재판단 동작을 따로 제공한다. 이미 닫힌 실패는 다른 부분의 취소·재개에 포함하지 않는다. 저장을 재개한 뒤 아직 판단하지 않은 부분이 남아 있으면 AI 이용 가능성도 안내한다.

관계 명령은 `POST .../memory/batch-run/{request_id}/{retry|cancel}`, 기억 저장 명령은 `POST .../memory/processing-runs/{run_id}/command`를 사용한다. 원래 범위에 없는 입력을 재시도에 더하지 않는다. 앞으로의 자동 예약 해제와 이번 요청 취소는 별개다. 종료를 위해 AI 설정이나 키를 다시 준비할 필요는 없다.

## 저장소와 검증 범위

PG schema v3→v4는 기존 데이터에 `maintenance` 제어 필드와 공용 슬롯을 추가한다. v4→v5는 기존 제어 필드에 과거 실패 제외 근거를 기록하고 자동 집계된 후속 요청 상태를 보정한다. 원래 SQLite migration snapshot은 바꾸지 않는다. 받은 결과 저널은 runtime의 실제 media 경로에 명시적으로 연결한다. 이미지 교체 시 옛 이미지 내부 저널을 백업하고 검증한 사본을 이전한다.

검증은 관련 상태 전이·실제 PG 충돌·schema 업그레이드·한영 복구 UI·휴대폰 최신 복제본에 한정한다. 별도 30분 혼합 부하 시험, 원격 CI, main 반영과 정식 릴리즈는 포함하지 않는다.

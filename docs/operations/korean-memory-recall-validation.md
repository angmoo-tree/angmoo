# 한국어 기억 검색 공백 보완 검증

2026-09-10 · 로컬 브랜치 `fix/chat-retrieval-debugging` · S1 구현·검색 회귀 통과,
직접 사용자 검증 대기. 원격 제출은 수행하지 않았다.

## 적용 의미

기존 FTS5 AND 및 normalized substring 검색이 모두 0건일 때만,
`search_memory_items`가 한국어 공백 보조 검색을 요청한다. 색인 오류는
공백 보완의 실행 조건이 아니다. posts/thread 검색 및 모델 프롬프트는 유지한다.
모든 검색어 그룹이 일치해야 하며 부분 개념 OR 검색은 구현하지 않는다.

질의 그룹은 2~12개, 그룹 길이는 최대 64자이며 최소 하나의 4글자 이상
한글 그룹을 요구한다. 새로 공백을 연결한 표현의 시작은 단어 경계이고 끝은
단어 경계 또는 제한된 조사 앞이어야 한다. 조사 목록은 `에서는/에서/으로/
부터/까지/은/는/이/가/을/를/에/와/과/의/로/도/만`이다. 질의에서 조사나 개념을
삭제하는 형태소 분석·동의어 처리는 아니다. 이 목록은 언어적 모호성을 완전히
해결하지 않으며, 짧은 단일 질의 및 다른 어미는 계속 놓칠 수 있다.

공용 정규화·색인 schema·generation은 변경하지 않는다. 파생 문서가 이미
공백을 합쳐 저장하기 때문에 없어진 원래 줄 경계를 복원할 수 없다. 현재
대상은 하나의 기억 요약인 `memory_item`이고, 제목과 본문을 합친 POST에는
보조 경로를 적용하지 않는다. 남아 있는 문장부호·필드 구분자는 연결하지 않는다.

## 처리량과 진단

한글 그룹에서 최대 4개 문자를 골라 SQL의 필요조건으로 사용한다. 공백 변화가
이 문자를 새로 만들거나 지우지 않으므로 이 사전 조건은 정확한 보조 일치를
제외하지 않는다. 문서를 최신 N개로 잘라 놓고 과거 전체를 찾았다고 하지 않는다.

SQL 실행·정렬 시간을 포함한 보조 deadline은 50ms다. 후보 행은 하나씩 읽고
최대 2,000행/UTF-8 정규화 텍스트 4MiB를 검사한다. 기존 반환 후보 상한은
`min(200, limit*4)`로 유지한다. 조회 전체가 50ms라는 의미는 아니다. 기존
normalized substring의 전체 scope 읽기 비용은 여전히 존재한다.

`korean_spacing_fallback` 관측은 `groups`, `scanned`, `bytes_scanned`,
`returned`, `elapsed_ms`, `truncated`, `reason`을 포함한다. `scanned`는 Python이
검사한 후보 행이며 SQLite가 내부적으로 살펴본 전체 행 수가 아니다.
`row_budget/text_budget/time_budget`에서는 잠정 후보를 버리고 typed
`MemoryRecallSearchIncomplete` → `DEGRADED / memory_recall_search_incomplete`로
전달한다. 전체 완료 0건과 구별된다. 원문/권한 재검증은 기존 경로를 유지한다.
기본 진단에는 검색어나 기억 본문을 넣지 않으며 상세 진단을 켠 요청만 기존
search_text와 보조 그룹 표현을 보존한다.

## 평가와 한계

- 12개 합성 경험의 60개 고정 질의, 경험 단위 조정 40/보류 20.
- 각 경험에서 정확 검색·붙여 쓰기·여러 공백·필수 개념 누락·없는 개념 추가를 비교.
- B0는 정답 질의 36개 중 24개 회수, 공백 변형 12개 누락.
- B1은 36개 모두 회수, 정답 없는 24개는 모두 0건 유지.
- 이는 색인 단계 Hit@5/Recall@5의 합성 측정이다. 60개 모두를 실제 LLM의
  자연어 질문이나 canonical 원문 검증으로 측정했다고 주장하지 않는다.
- 별도로 실제 임시 canonical SQLite → FTS5 → 원본 검증 → 상세 원문 →
  frozen evidence 연결과 기존 Chat 회귀를 검사한다.
- 새 후보가 삭제/숨김/digest/수명 검증을 통과하지 못하면 제외한다. 재검증 후
  0건이 됐다고 다시 조건을 완화하지 않는다.
- 시간 범위는 현재 `CanonicalRecallQuery`에 있지만 기존 색인 검색 계약에는
  전달되지 않는다. 이번 보조는 시간 조건이 있는 요청에 활성화하지 않는다.
  기존 검색의 시간 조건 전달 누락을 이 변경으로 해결했다고 하지 않는다.

## 성능 기록

첫 12회 측정에서 1만 문서의 전체 검색 p95가 B0 122.38ms/B1 205.55ms로
증가 기준 25ms를 넘었다. 이 실패를 보존한다. 이후 기준을 낮추지 않고 60회
최근접 순위 p95와 보조 단계 시간을 분리해 재측정한다. 단일 최고값의 원인을
확정하지 않으며, 초기 실패만으로 새 단계 자체가 83ms였다고 주장하지 않는다.

60회 재측정 결과(동일 Windows 기기, 합성 자료, 검색 단계만 측정):

| 문서 수 | B0 p50 / p95 / p99(ms) | B1 p50 / p95 / p99(ms) | 보조 단계 최대(ms) |
| --- | --- | --- | --- |
| 1천 | 12.291 / 16.206 / 18.522 | 13.469 / 17.085 / 22.817 | 1.412 |
| 1만 | 105.290 / 136.986 / 163.427 | 115.229 / 149.582 / 162.384 | 14.839 |

p95 증가 0.879ms / 12.596ms로 기존 25ms 기준을 충족했다. 기존
전체 fallback 비용이 포함된 수치이며 실제 채팅 전체 응답 시간은 아니다.
오래된 정답은 관계없는 1천/1만 문서 뒤에서도 회수했다. 필요조건을 만족하는
문서가 2,000행을 넘으면 완전 검색으로 가장하지 않고 incomplete로 처리한다.

최종 선택은 S1이다. 로컬 코드와 Docker 실행 파일 5개의 줄바꿈 정규화 SHA-256이
일치하고 backend/frontend healthy 및 3000 HTTP 200을 확인했다. 실제 색인도
`mode=ro + query_only`로 대조해 붙여 쓴 검색이 0→목표 기억 1건, 기존 엄격
검색은 1→1건임을 확인했다. 이 대조는 사용자 요청 재전송이나 답변 생성이 아니다.

최종 측정·USER CHECK 상태는 실행 계획의 실행 기록과 함께 관리한다.
외부 provider 호출은 이 자동 검증에 사용하지 않는다. S2 부분 일치 및 P1
프롬프트 변경은 실사용 잔여 실패 근거를 확보하기 전에는 진행하지 않는다.

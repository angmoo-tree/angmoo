## 문제와 변경

기존 배치 함수는 여러 준비된 입력을 받으면 묶어서 전송했다. 그러나 상황기억 작업은 한 건을 반영한 뒤 매번 느린 기억 요약 갱신을 수행했고, 벡터 작업자는 그 사이 한 건씩 가져갈 수 있었다. 준비된 입력을 배치 함수에 직접 넘기는 기존 시험만으로는 이 실제 연결부를 검증할 수 없었다.

상황기억 작업은 한 차례에 최대 32개 접수 기록을 처리하고, 각 기록마다 기존 검증·별도 commit·lease 해제를 유지한다. 기억 요약 갱신은 이 유한한 처리 차례가 끝난 뒤 한 번 수행한다. 채팅이 진행 중이면 기존처럼 상황기억 반영과 느린 요약 갱신을 함께 보류한다. 이 32는 내부 작업 처리 예산이며 API 묶음 상한과 다르다.

벡터 작업자는 같은 정리 요청에서 적용·등록된 첫 전송 항목들을 모델별 상한까지 모은다. 해당 요청의 기존 cutoff 안에 이미 접수된 항목만 기다린다. 상한에 도달하거나 요청이 완료·오류 상태가 되면 준비된 항목을 전달한다. 새 요청이나 미래 SNS 활동이 생기기를 기다리는 고정 지연을 추가하지 않는다.

상황기억 등록은 이미 원본 반영과 같은 transaction에서 이루어진다. 변경 큐의 순차 확장이 아직 도달하지 않은 같은 요청의 등록 항목도 함께 선택할 수 있다. 새 작업 등록 직전에는 원본 등록·삭제 상태와 World 삭제 접수를 짧은 writer에서 다시 확인한다. 별도 영속 큐·표·스키마·이력 재작성은 추가하지 않았다.

이미 시도한 항목, 저장 재시도, 만료된 claim, 삭제·변경 처리는 기존 경로를 사용한다. API 호출 전과 벡터 저장 직전의 출처·권한·현재성 검증은 기존 코드가 계속 소유한다. 받은 결과 보존, 항목별 짧은 canonical→Vec1 저장, 중복 호출 예산도 유지한다. 배치 준비 상태는 권한 검증의 대체물이 아니다.

## 모델별 전송 계약

Gemini embedding 2는 기존의 보수적인 Angmoo 상한을 유지한다.

- 요청당 독립 입력: 최대 **20개**.
- 입력 하나: UTF-8 **8,192바이트** 이하.
- 요청: JSON escaping 및 항목별 envelope를 포함한 보수적인 **65,536바이트** 예산.
- 33개의 짧은 입력: **20개 + 13개**, 총 2회 요청.
- 긴 입력: 개수 상한 전이라도 크기 예산에 따라 분할한다.

이는 Google API의 공식 최대치를 뜻하지 않는다. 이미 지원·검증된 앱 한도를 유지해 한 요청의 크기와 실패 영향을 제한한다. 독립 `Content`를 사용해 각각의 벡터를 받는 방식은 [Google 임베딩 안내](https://ai.google.dev/gemini-api/docs/embeddings)와 기존 SDK 구현을 대조했다.

상한은 Runtime에 Gemini 숫자를 복제하지 않고 모델 registry의 capability·limits와 실제 adapter 메서드에서 읽는다. 단건 전용 adapter는 단건 처리를 유지한다. 새 모델을 실제로 지원하려면 그 모델의 기존 registry/adapter 계약을 추가·검증해야 하며, 이번 변경이 미지원 모델을 자동으로 지원한다는 뜻은 아니다.

## 검증 방법과 결과

새 시험은 수동 정리 접수에서 시작한다. 실제 SQLite에 접수·상황기억·등록·claim을 저장하고 각 항목 commit 직후 벡터 worker를 실행하여, 이전의 단건 분산이 재현되기 쉬운 실행 순서를 강제한다. 기존 Google SDK가 생성한 HTTP 요청을 `httpx.MockTransport`에서 확인한다. 실제 AI 서버나 사용자 API 키는 사용하지 않는다.

| 입력 조건 | 관측한 HTTP 묶음 |
| --- | --- |
| 같은 조건의 짧은 기억 1개 | `[1]` |
| 같은 조건의 짧은 기억 2개 | `[2]` |
| 같은 조건의 짧은 기억 4개 | `[4]` |

각 응답의 서로 다른 벡터 값을 실제 전달된 기억 ID·본문과 대조했다. 정리 도중 별도의 SQLite writer가 매 항목 사이에 진입할 수 있는지도 확인했다. 정리 일부가 실패하면 이미 준비된 기억을 전달하고, 응답 도중 삭제된 기억은 복구하지 않는다. 응답 후 writer 경합이 발생한 경우 received journal을 재사용하여 추가 HTTP 없이 저장했다.

기본 통합 시험의 canonical DB는 실제 파일 SQLite이며, 벡터 대응 검증은 영속 인덱스 시험 구현과 실제 `upsert` 입력을 사용한다. 실제 Vec1 DLL의 잠금·저장 보호는 별도 경합 시험으로 확인했다. 사용한 기존 DLL의 SHA-256은 `4bc0b513e9b6a630159212452ff3fc70b86d89c6ef63f6ea92ae075599e65303`이며, 기존 manifest와 대조했다.

## 아키텍처 검사 및 적용 범위

현재 import inventory를 재생성했다. 전체 경계 검사는 기존 `memory_pipeline_observation` ↔ `sns_observation` 순환 의존 한 건을 보고한다. 기존 baseline 파일만 보면 발견되지 않던 항목으로, 변경 전 HEAD의 실제 소스에서 inventory를 새로 구성해 대조해도 동일한 오류가 나온다. **이번 변경으로 추가된 경계 위반은 0건**이며, 기존 오류를 예외 처리하거나 검사에서 숨기지 않았다. 이 두 관찰 파일의 소스는 수정하지 않았다.

로컬 격리 시험의 PASS와 사용자 Docker의 실제 적용은 구분한다. 초기 구현 검증 당시에는 컨테이너에 데이터 볼륨만 마운트돼 있고 소스 bind mount가 없었으며, 이미지를 재빌드·교체하지 않았으므로 실제 적용과 AI 호출은 미측정이었다. 이후 적용 확인과 수동 실행의 실측 결과는 다음과 같다.
